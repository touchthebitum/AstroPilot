Interpretation
Provenance scans remain measurable during creation, but do not explain 40 s
in this compatible reproduction. No evidence of a 40 s lock or timeout here.
The writer file lock is nonblocking; Guardian serializes commands with RLock.
This audit does not eliminate contention, Cocoa-wrapper behavior, browser
behavior, or a different dataset in the original running instance.
Complete copied data is incompatible with the selected base; that is a proven
environment/data issue, not a proven root cause for the reported successful start.
Before/after latency improvement: N/A. No backend performance behavior changed.

Verified fixes
ASTROPILOT_SESSION_TIMING=1 now activates the existing UI fetch timing logger
in the served document, and Server-Timing also covers execution discovery.
Previously server opt-in did not enable UI logging; manual console activation
was necessary. Without the flag, no diagnostic script/header is emitted.
The saved-mission button starts disabled, is enabled only for a valid selected
persisted mission, updates on selection changes, and cannot fall back to a
previously accepted mission when selection is invalid. Active state has readable
text, cyan background/border, pointer, hover and keyboard focus. Disabled state
has muted text, opacity and not-allowed cursor.
Fail-closed responses and the start/renewal command sequence are unchanged.

Follow-up for original-instance diagnosis
Restart the exact clean base with the complete production-compatible dataset,
ASTROPILOT_SESSION_TIMING=1 and explicit Guardian renewal/path variables.
Capture the console session-request entries from the actual slow click, matching
execution ID, server durations, HTTP statuses and runtime build. A 40 s client
request with a short server duration directs investigation toward browser/network;
a 40 s server duration identifies which endpoint to profile. Preserve the
incompatible files separately before any future migration; do not patch schema
numbers or suppress provenance validation.
